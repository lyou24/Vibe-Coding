# 個人用食事記録アプリ 開発仕様書

状態：v1.1・端末内で使える初期実装済み。Gemini APIを呼び出すサーバー側下書きAPIと写真・文字入力画面を実装済みだが、APIキー未設定のため実解析は未接続。クラウド保存・Obsidian自動取り込み・本人専用ログイン・写真履歴保存は確定要件だが未接続。iPhoneで1日3〜5回、Gemini無料APIでアプリ内解析し、上限時は手入力。無料枠のデータ利用条件は確認済み。技術提供元の最終構成選定を残す。

## 1. 意図・コア体験

広告なしで素早く記録し、蓄積データを自分で取り出せる個人用アプリ。よく食べる料理は保存済みの値を再利用し、入力負担とAI解析回数を減らす。

## 2. 構成・技術選定

論理構成案：スマホWeb UI → 認証済みサーバー → 画像対応AI／食事DB／非公開画像保存先。

| 項目 | 方針・確定状態 |
|---|---|
| 配置 | 独立アプリ。作業ルートは C:/Users/lyoul/AI_Project/90_Git/meal-tracker/。他プロジェクトに変更を加えない |
| フロントエンド | スマートフォン中心のWebアプリ。PWA対応を提案。フレームワークと版は未選定 |
| データ | 食事DBを正本とするクラウド方式。CSV/JSON出力とObsidian自動取り込みを実装対象とする |
| AI | Gemini API無料枠をサーバー経由で利用。画像対応モデルと実際の上限は着手時に確認。無料枠データ利用条件は了承済み |
| 認証 | 本人のみのアクセスをサーバー側で強制。方法は未選定 |
| 秘密情報 | クライアント・Git・ログ・.envへ保存せず、実行環境の安全な秘密情報管理を使用 |

## 3. 画面と操作

| 画面 | 内容・挙動 |
|---|---|
| 今日 | 日付、kcal/P/F/C/食塩相当量とC内訳（糖質・食物繊維）、当日に有効なカロリー/PFC目標と実績、食事区分ごとの記録。「写真」「文字」「よく食べるもの」から追加 |
| 食事入力 | 写真と補足文字を併用可。メニュー表の場合は食べた料理を選択。日時・食事区分・摂取量を指定 |
| 解析確認 | 料理名、量、栄養値、根拠区分、不足情報を編集。保存するまでは日計に反映しない |
| よく食べるもの | 名前検索、並べ替え、追加・編集・削除。1タップ追加と詳細編集を別操作にする |
| 履歴・詳細 | 日付別一覧、料理明細、修正・削除。定型メニュー登録にも進める |
| 設定・データ | カロリー/PFC目標の設定・変更・履歴、ログイン、写真方針、AI利用状況、CSV/JSON出力・JSON復元、同期状態 |

定型追加では表示中の日付・選択中の食事区分を使用し、未選択時は時間帯に応じた区分を表示して追加する。完了表示に日付・区分と「取り消す」を出す。定型メニューの編集は過去記録に波及させない。

初版UIはライトテーマを基準とする。デスクトップは横幅を制限し、スマホでは1列表示。固定操作部分はセーフエリアとソフトウェアキーボードを考慮する。

## 4. 入力・AI解析パイプライン

1. 写真をプレビューし、回転・削除・補足入力できるようにする。画像形式・容量上限は対象端末確定時に決める。対応外の画像は送信前に案内する。
2. 位置情報等の不要な画像メタデータを除去し、解析用画像へ縮小する。本人の写真・文章を外部AIへ送る条件は事前確認する。
3. AIは料理候補・分量・栄養値・前提を構造化出力する。画像やメニュー内の命令文はデータとして扱う。
4. サーバーで形式、単位、有限数、負数、不合理な値を検証する。推測が困難な項目はnullと不足理由を返す。
5. 解析結果を未保存ドラフトとして表示。料理の追加・削除・分量変更・栄養値の直接修正を可能にする。
6. 確認後、料理明細と食事を一括保存。リクエストIDにより連打・再送の重複保存を防ぐ。

解析状態：未入力 → 入力済み → 解析中 → 要確認 → 保存中 → 保存済み。失敗時は入力済みまたは要確認へ戻し、理由・再試行・手動入力を提示する。

タイムアウト・回数上限・提供元障害では保存済み記録に影響させない。自動再試行は有償呼び出しの重複を避け、同じ入力の再解析は利用者の操作を基本とする。予算確定後、回数・トークン上限をサーバー側に設ける。アプリ外の課金や料金変動まで完全に防げるとは表示しない。

## 5. 栄養・計算仕様

- 内部単位：energy_kcal、protein_g、fat_g、carbohydrate_g、salt_equivalent_g、available_carbohydrate_g（糖質）、dietary_fiber_g（食物繊維）の計7項目。
- Cの下に「うち糖質」「うち食物繊維」を常時表示。糖質と糖類は別項目として扱い、糖類を糖質へ代入しない。糖質のみ判明してもCの確定値にはしない。C・糖質・食物繊維は別々に出典とnullを保持し、初版では差し引きによる自動補完をしない。内訳の合計とCに差があれば確認表示し、丸め・測定基準差を無視した強制補正はしない。内訳編集でもCを自動変更せず、修正値を確認して保存する。Cと内訳を二重加算しない。
- 「塩分」の画面表記は「食塩相当量」に統一。ナトリウム入力の換算を実装する場合は、採用する換算式と根拠を公式資料で確認して仕様追加する。
- 栄養値は基準量と摂取倍率を持つ。既定1食・半量・2食・g指定に対応し、重量が不明な料理にg換算を強制しない。
- 合計は保存済みの摂取量換算値から計算し、表示段階で丸める（kcal整数、g小数1桁を提案）。不明値はnullのまま保持する。
- 表示上の丸め差を許容し、PFCから逆算したエネルギーで表示資料のkcalを勝手に上書きしない。
- 食事日時はタイムゾーンと記録日を保持し、初期値はAsia/Tokyo。午前0時を跨ぐ操作や過去日への追加で記録日が変わらないようにする。

### 5.1 カロリー・PFC目標と適用日の管理

- 目標は1日単位でenergy_kcal、protein_g、fat_g、carbohydrate_gを保存し、設定から変更する。初回は空欄とし、既存プロファイルの目標を無断採用しない。
- g入力モード：カロリーとP/F/Cのgを入力し比率を参考表示。比率入力モード：カロリーと合計100%のP/F/C比率から目標gを算出する。比率計算専用係数はP=4、F=9、C=4とし、これは目標設定UIの計算規則であり食事実績のkcalを変更しない。
- 比率表示は4P・9F・4Cの合計を分母にする。入力した目標kcalと4P+9F+4Cの差は案内し、自動上書きしない。比率は0以上100以下・合計100%（許容誤差0.01ポイント）、目標kcalは正の有限数、gは非負の有限数。空欄・全PFCゼロは保存不可。
- 保存時のサーバー基準Asia/Tokyoの「今日」をeffective_from（適用開始日）とし、当日0時から日全体に適用。初版は過去日への遡及変更・未来日予約を設けない。
- 画面に「今日から適用。昨日以前は変更しません」と適用日・新旧値を表示。午前0時を跨ぐ保存は新しい適用日を示して再確認する。
- 新目標は追記し、旧レコードを上書き・削除しない。同日に複数回変更した場合は最後に確定したrevisionをその日全体に適用し、途中の値も監査履歴として保持。
- 対象日Dにeffective_from <= Dの目標を抽出し、effective_from降順、同日内revision降順の先頭1件を採用。前の有効期間は次の適用開始日の前日まで。終了日を重複保存しない。
- 過去の食事を後日追加・修正しても、編集日ではなく食べた記録日の目標で比較。期間集計を行う場合は日別目標を合算し、最新目標×日数にしない。未設定日は比較対象から除外し、対象日数を示す。
- 目標未登録期間は「目標未設定」と実績のみ表示し、達成率・残量を算出しない。未来の目標を遡って埋め戻さない。各目標0の場合の達成率は「—」とし、0除算を防ぐ。
- 複数端末の競合はownerごとのrevisionをトランザクションで発行し、更新元revisionの不一致時は再読込を案内。同一リクエストIDの再送は1回だけ保存。
- オフラインでは目標の編集内容は下書きに留め、有効目標を切り替えない。再接続後の明示保存日から適用し、当初の編集日に遡らない。
- 当日サマリーは変更成功後に再取得。目標変更で食事のkcal・栄養実績を変えない。
- 初版で編集必須の目標はカロリーとP/F/C。糖質・食物繊維・食塩相当量は実績表示対象。

## 6. データモデル（論理案）

| エンティティ | 主な属性 |
|---|---|
| Meal | id、owner_id、食事日時、記録日、タイムゾーン、区分、メモ、作成/更新日時、revision、削除状態 |
| MealItem | id、meal_id、料理名、基準量・単位、摂取倍率、栄養7項目、根拠区分・参照情報、推定前提、修正状態 |
| Favorite | id、owner_id、名称、料理明細の雛形、既定量、並び順、版 |
| Attachment | id、meal_id、非公開保存キー、形式、容量、保存/削除状態 |
| Analysis | id、owner_id、状態、モデル・解析日時、推定ドラフト、利用量。生画像・全文のログ出力は禁止 |
| NutritionTargetVersion | id、owner_id、effective_from（JST日付）、revision、目標kcal/P/F/C、入力モード、元の比率、作成日時、request_id。追記のみ |
| Export/Sync | schema_version、生成日時、同期カーソル、失敗理由。秘密情報を含めない |

MealItemは記録時点のスナップショットとして保存し、Favoriteの変更から独立させる。栄養項目ごとに根拠区分を保持し、塩分だけ推定といった混在に対応する。

## 7. 外部出力・蓄積・削除

- CSV：UTF-8、1行1料理。食事ID、日付、区分、料理名、量、栄養、根拠、不明状態を出す。表計算で数式として実行される文字列を無害化する。
- JSON：schema_version、食事、料理明細、定型メニュー、根拠、日時、ID、栄養7項目、全目標revision・適用開始日・入力モードを保持する完全データ形式。写真を残す方式では画像一式と対応表を合わせたバックアップも提供する。
- 目標CSVはtarget_history.csvとして全変更履歴を出力。食事CSVには栄養7項目と、その記録日の有効目標ID・目標kcal/P/F/Cを含める。Obsidianにも目標変更イベントを追記し、適用日を保持する。
- 復元：ファイル形式・版・値を検証し、取り込み件数と競合をプレビューして実行する。既存データを置き換える場合は確認する。
- 自動取り込みはクラウド → PCの保管庫の一方向とする。PC停止中はクラウドで蓄積し、復帰時に再開する。PC稼働中は15分間隔と起動時の同期を設計値とする。最終成功時刻と未同期状態を見えるようにする。
- 同期はID・revision・削除状態に基づき、同じ記録を重複させない。Layer 2の記録先では訂正・削除イベントを追記し、過去ログを上書きしない。具体的出力ノートは未確定。
- 食事削除では日計から除外し、関連画像の削除も処理する。バックアップ・保管庫に残るコピーへの影響を明示する。同期用の削除マーカーは画像や本文を含まない最小情報で保持し、長期停止PCへの削除反映に用いる。写真は本人削除まで保存し、容量上限時には新規画像保存を止め、本文だけの記録を選べるようにする。
- 旧形式の取り込みで糖質・食物繊維や目標履歴がない場合はnull/目標未設定を維持。目標復元は日付・revision・所有者・全履歴の整合性を検証する。目標履歴については一般の記録置換と区別し、初版では既存の有効目標を変える競合取り込み・上書きを認めない。同一IDかつ同一内容は読み飛ばし、不一致は取り込みを中断する。未登録の期間へ履歴を復元する場合は、適用日と影響する期間を事前表示する。空の保存先への完全復元は元IDと全revisionを保持する。
- 外部出力は画面キャッシュではなく、本人の全保存データを取得する。

## 8. 先祖返り禁止事項

- 広告・第三者広告追跡を入れない。データ出力機能を後から失わせない。
- 推定値を測定済みと表現しない。不明を0に変換しない。
- メニュー表全体の自動記録、再送による二重記録をしない。
- 定型メニューの変更で過去の栄養記録を変えない。
- 目標変更で前日以前の目標を変えない。現在目標を過去へ一律適用しない。Cに糖質・食物繊維を二重加算しない。
- UI上の非表示だけで認証を代用しない。画像・バックアップも本人限定とする。
- 認証情報や画像を公開Git・ブラウザ配信コードに含めない。
- 保存方式・予算が未決のまま、特定サービスへの依存を確定しない。

## 9. 自動検証・UI受入基準

| ID | 検証内容 | 合格条件 |
|---|---|---|
| A01 | 写真・文字・メニュー表 | 3経路で入力・確認・保存・再表示が成功し、選択した料理だけが記録される |
| A02 | 分量変更・未知値 | 半量/倍量が全既知項目に反映。不明項目は不明のままで日計にも未入力を表示 |
| A03 | 定型メニュー | 1タップで1件追加でき、取り消し可能。雛形編集後も過去記録は変化しない |
| A04 | 永続化・編集 | 再読み込み後も残り、編集・削除が日計に反映する |
| A05 | 二重送信・競合 | 連打・通信再送で重複しない。複数画面からの古い更新を黙って上書きしない |
| A06 | 出力・復元 | 日本語・小数・null・根拠を含む食事/定型のJSON往復で情報が一致。画像保存時は画像も復元できる |
| A07 | 通信・AI失敗 | 入力が残り、未保存表示と手動入力導線が出る。解析失敗を栄養0として記録しない |
| A08 | アクセス制御 | 未ログイン・別所有者の食事/画像/出力/APIへのアクセスを拒否する |
| A09 | スマホ表示 | 幅360/390/430pxとPCで横スクロール・重なりなし。200%文字拡大でも主要操作可能 |
| A10 | 実端末 | 指定スマホのブラウザとホーム画面起動で撮影/選択/保存/出力を確認 |
| A11 | 品質 | 型チェック・Lint・主要ロジックテスト・本番ビルドが成功。主要DOMが存在し、操作時コンソールエラー/警告0件 |
| A12 | 自動同期 | PC停止中の記録が復帰後に重複なく取り込まれ、訂正・削除イベントも反映する |
| A13 | 栄養7項目 | 写真/文字/メニュー表、手入力、定型、履歴、CSV/JSON、同期で糖質・食物繊維も保存表示。nullは0にならず、Cの二重加算なし |
| A14 | 日付境界の目標 | 9/21旧目標、9/22変更後、9/23新目標を表示。9/21の食事を9/23に追記しても旧目標との比較を維持 |
| A15 | 同日変更・未設定 | 同日2回変更後は最後の値を当日全体に適用。全revision保持。初回設定日前は未設定 |
| A16 | 目標入力 | g/比率、比率合計、不正値・0除算防止、日付跨ぎ・競合・再送・オフラインの保存を確認 |
| A17 | 目標の可搬性 | JSON復元とObsidian同期後も日別目標と全revisionが一致。CSVに適用日と対応目標を保持 |

検証用の栄養データは架空データと明示する。単位換算・丸め・日付境界・欠損・復元・アクセス制御を重点的に自動テストする。実データで未検証のAI精度や応答秒数を保証しない。

## 10. 開発手順と判断履歴

順序：回答反映 → 技術・費用・保持条件検証 → 仕様確定 → 入力/定型/保存の実装 → AI/出力/必要な同期 → 独立検証 → 実端末確認 → 公開。

実装担当と独立監査を分ける。検証不合格は最大3回の局所修正と再検証を行い、期待値を下げない。利用可能モデルの範囲で役割分担し、利用不可のモデルを使用済みと記録しない。

### 設計判断 ADR-001：記録の正本と外部可搬性

アプリ外へデータを蓄積したいという目的から、CSVに加えて完全復元用JSONとObsidian自動取り込みを採用。クラウド保存だけで要望を満たしたことにしない。

### 設計判断 ADR-002：解析と保存を分離

料理・分量・摂取対象の誤りを修正できるよう、AI結果をドラフトとして扱う。定型記録は確認済みの雛形から直接追加し、操作数を抑える。
